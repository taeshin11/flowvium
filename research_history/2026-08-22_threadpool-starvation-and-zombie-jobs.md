# 2026-08-22 — 타임아웃은 취소가 아니다: libuv 스레드풀 기아와 5시간 좀비

## 요약

내가 어제 넣은 백업 검사 하나가 모니터를 6시간 눈멀게 했고, 같은 뿌리에서
예약 백업 잡이 5시간 좀비로 남아 있었다. 원인은 하나다 — **취소할 수 없는 파일시스템
연산에 타임아웃을 걸고 취소했다고 믿은 것.**

## 증상 두 개

1. `cron.log` 에 `[auto-monitor] stall=TIMEOUT(hang)` **17회**.
   08-21 23:03 KST 부터 20분마다. 대화형 셸에서 `check-stall.mjs` 는 2초에 끝난다.
2. `launchctl list` 에 `com.spinai.flowvium-backup` 이 PID 를 물고 있음.
   `ps` 로 보니 **5시간 0분** 경과. 그런데 `backup.log` 는 00:57 에 이미
   `총 소요 60.4s / ✅ 인수인계 백업 완료` 를 찍었다. 일은 끝났는데 안 죽는다.

## 추적

### 1. 어디서 멈추나 — 감으로 고르지 않고 launchd 안에서 쟀다

대화형 셸에서는 재현이 안 되므로 임시 launchd 잡(`com.spinai.stallprobe`)을 띄워
단계별로 계측했다.

```
resource-pressure   0초
backup-health      10분+ 미완료      ← 여기
```

`backupStatus()` 가 Google Drive 경로에 `readdirSync` 를 **상한 없이** 걸고 있었다.
launchd 컨텍스트에서 Drive 왕복 연산이 안 끝난다는 건 전날 직접 측정해 두고서,
`backup-takeover.mjs` 에만 상한을 넣고 정작 *판독기* 에는 안 넣었다.
— 한 곳만 고치고 나머지를 안 보는, 이 저장소의 반복 패턴.

### 2. 1차 수정이 불충분했다

`Promise.race` 로 5초 상한을 걸었다. 함수는 5초에 돌아온다. 그런데 launchd 에서
node 프로세스가 **3분 넘게 종료되지 않았다**. 그리고 그 사이 cron 사이클
(20:43 UTC)은 부분 출력을 다 찍고도 여전히 `stall=TIMEOUT(hang)` 으로 끝났다 —
내 프로브와 무관한 독립 증거였다.

### 3. 진짜 기전 — `sample` 로 스레드를 떴다

```
$ sample 31735 3
총 11 스레드
  libuv-worker  ×4  — 전원 uv__fs_work → open()/unlink() 커널 대기 (Drive 경로)
```

**기본 스레드풀(4) 전부**가 막혀 있었다. node 의 fs 비동기 연산은 스레드풀에서 돌고,
한 번 커널에 들어간 요청은 취소할 방법이 없다. 타임아웃은 *기다리기* 를 그만둘 뿐
*작업* 을 취소하지 못한다.

그러면 `backup-takeover.mjs` 의 마지막 두 줄이 이렇게 죽는다:

```js
await fsp.unlink(localDb)   // 219행 — 로컬 임시본. 슬롯이 없어 스케줄 자체가 안 된다
process.exit(0);            // 220행 — 영영 도달하지 못한다
```

**로컬** 경로인데도 못 돈다. 슬롯이 없기 때문이다.

### 4. 더 나쁜 사실 — `process.exit(0)` 도 탈출구가 아니다

나는 77행 주석에 이미 이렇게 써 뒀었다:

> race 는 밑에서 도는 연산을 취소하지 못한다 — 스레드풀에 남는다.
> 그래서 마지막에 process.exit 로 명시 종료한다.

절반만 이해했다. FIFO(명명 파이프)로 같은 상태를 로컬에서 결정적으로 재현해 쟀다 —
읽기용 `open` 은 쓰는 쪽이 붙을 때까지 커널에서 막히므로 Drive 와 같은 상태가 된다.

```
process.exit(0)                 → 6초+ 미종료, 외부 SIGKILL 필요 (rc=137)
process.kill(self, 'SIGKILL')   → 0.46초
```

libuv 가 종료 시 워커 스레드를 join 하기 때문이다. 즉 완화책의 전제가 처음부터 틀렸다.

## 조치

**취소 가능한 유일한 경계는 프로세스 경계다.**

- `backup-health.mjs` — 원격 목록/타임스탬프 조회를 `execFile(timeout, SIGKILL)` 자식으로.
- `backup-takeover.mjs` — Drive 를 만지는 데이터 연산(cp/rm/ls/mkdir)을 전부 자식으로.
  종료 직전 정리는 `unlinkSync`(동기 호출은 *호출 스레드* 에서 돌아 기아와 무관).
- 순서 교정 — 로컬 2차 백업이 **Drive 를 한 번이라도 만지기 전에** 끝난다.
  동기 메타데이터 연산도 막히면 메인 스레드를 세우고, 그러면 유일한 안전망도 못 만든다.
- 실패 사유 구분 — 자식 SIGKILL 만 '상한 초과' 로 세어 회로차단기에 넣는다.
  전부 뭉뚱그리면 디스크 부족까지 "Drive 권한 문제" 로 오진하고 로그가 거짓말을 한다.
- 등급 분리 — 원격을 '못 읽은' 것은 로컬이 신선하고 복원 가능하면 결함이 아니다.
  🚨 를 띄우면서 본문에 '정상' 이라 쓰면 늑대소년이고, 진짜 결함이 묻힌다.
- 감시자(reaper) — Drive 가 동기 메타데이터까지 멈추는 날엔 이 프로세스 안의 어떤 JS 도
  우리를 못 구한다(process.exit 조차). 그래서 밖에 둔다. PID 재사용 오살을 막으려
  명령줄을 확인하고 죽이며, 해제할 때는 **그룹째** 죽인다 —
  `reaper.kill()` 은 sh 만 죽여서 자식 `sleep` 이 고아로 남는다(실측 2개).

## 일반화 — `check-stall [10] 좀비 잡`

원인(스레드풀 기아)은 고쳤지만 *다른 이유로 같은 증상* 이 나면 또 5시간을 모른다.
검사 9종 중 프로세스를 보는 건 `[3]` 뿐이고 그건 report-gen 전용이었다.

'주기 잡인데 주기보다 오래 산다' 는 원인과 무관하게 같은 신호이고 조치도 같다.
`scripts/lib/stale-jobs.mjs` 로 일반화했다. 임계값은 코드가 아니라
`data/resource-thresholds.json` 의 `jobs` 절 — 코드에 박으면 다음 사람이 못 찾는다.
상주 데몬은 허용목록으로 제외한다. 오경보가 울리는 모니터는 곧 무시된다.
